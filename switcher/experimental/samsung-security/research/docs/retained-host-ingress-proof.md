# Retained host request-ingress readiness

**The original parent can remain operational as a retention candidate, but a blanket host-fork, AMS or host-UI stop is incompatible with known required security requests. A safe foreground-only admission policy is not yet implementation-ready from the reused proofs.** The finite next cut is the actual semantic request-to-process path, beginning with Samsung's explicit biometric service bind, not another PID/UID allowlist or a pause/success API. This finding neither selects retention nor affects the pending capture diagnostic approval.

This reuses original Samsung services `def967fb…` and framework `8095a9ae…`, the existing users/AM, biometric, policy and quiescence contracts, and the exact installed OneOS 0.4.57 stop patterns. The [inventory](../inventory/retained-host-ingress-proof.json) distinguishes checked method bodies from declarations and missing behavior. No new source queries, process starts, Binder/HAL calls, phone operations, script execution, Git or canonical changes were performed.

The source-supported mandatory cohort is finite by role, not a list of permitted process names:

| --- | --- | --- |

LSS's real `unlockUser2` request and listener/tails cannot be replaced by guest progress or an empty queue. | A complete AMS/ATMS start/fork discriminator or every transitive process. |
| Fingerprint/Biometric/Auth → `SemBiometricSysUiManager.openSession` → `bind` | The genuine biometric UI connection, session and physical display/input/power collaborators, including a disconnected endpoint's real service-resolution path. | That the UI is currently resident, a new fork always occurs, or allowing its package alone provides physical handoff. |

The first decisive body is concrete. `SemBiometricSysUiManager.openSession` invokes `bind()` at PC120. The disconnected/waiting guards precede construction of the explicit component `com.samsung.android.biometrics.app.setting/.BiometricsUIService` at38/41. At57 the actual stored Context calls `bindService(Intent,int,Executor,ServiceConnection)` with literal flags603979777. Its Boolean result is not consumed; the body sets `mIsWaitingForConnection` at61 and posts a 3000ms timeout at69. Thus a generic “deny host app starts” rule is not a working biometric UI route, and returning false does not supply immediate completion. Never force a connected field or successful authentication to hide that failure. Prewarming one process would not prove its later missing/restarted-connection path unnecessary.

DPMS supplies a second distinct ingress family. `reportFailedPasswordAttempt(IZ)` calls `sendAdminCommandForLockscreenPoliciesLocked` at131 after real state/policy handling; `reportPasswordChanged(PasswordMetrics,int)` calls it at136. These are genuine policy effects, not user requests to launch the host launcher. Actual administrators are resolved through the original loaded admin records and receiver/package permission checks. Their identities can belong to ordinary application UIDs. Dropping their work or authorizing a fixed “system UID” would change security semantics. The selected reports prove the command roots; their full broadcast and cold-process continuations remain a source frontier.

Telephony/SIM remains an explicit missing cohort. The existing scoped proofs do not close Samsung's telephony/SIM cold-start, death/restart and request-to-fork paths. The installed switch's `imsd` keepalive/start logic is not proof of the Java phone service, SIM state authority or all required receivers. Generic SIM restrictions establish a requirement, not a process inventory. Do not infer `com.android.phone` completeness, force a SIM-unlocked/default state, or classify all telephony work as optional. This missing source owner prevents claiming a complete host-ingress policy.

Ordinary host home/launcher/recents or unrelated user-selected application starts are a separate intended control domain. The reused raw Samsung AMS declaration actually contains `startActivity`, `startActivityAsUser`, `startActivityWithFeature`, `startService`, `bindService`, multiple `bindServiceInstance` overloads, and `broadcastIntent`/`broadcastIntentWithFeature`. The inventory records their exact descriptors. **Declarations are not dispatch/body proofs.** An AMS-only hook is not established as covering actual ATMS activity ingress, and a zygote request alone is not shown to retain enough reason to distinguish these uses. “Activity versus service,” foreground state, component string, process name, UID0/1000, or the guest-active flag is not that proof. A security-owned visible UI and a policy-selected receiver must not be mistaken for optional host presentation.

The minimal source-admission cut is therefore:

1. Follow the known bind57 call through the real original Context implementation into the matching Samsung AMS binding entry, actual service resolution and missing/restart process branch. Preserve the real live owner/session, caller, resolved component, user/profile and original PM/permission checks. No caller-supplied reason string/Boolean attests that origin.
2. Follow the two known DPMS admin-command roots into their actual receiver dispatch, and distinguish source-owned user/role/lifecycle continuations from ordinary foreground task requests. Preserve already accepted callbacks, connection failures and native/UI session outcomes. Do not wait on the Handler that must deliver them.
3. Pin the actual foreground activity/task entry and the selected process/zygote handoff before implementing refusal/defer behavior. A genuine source refusal or owned deferred request must retain its outcome; no forged ActivityManager success or discarded callback. Cached/local and reentrant paths must be covered, not only a newly published name.
4. Close the named telephony/SIM restart frontier and the real physical UI handoff before admitting the full guest-front policy. Existing display-plan disqualification is not repaired by allowing one service to fork.

This is a bounded next source selection, not a request for a whole-system fork audit. It starts from concrete captured callers and chooses their actual dispatch continuations. Keeping the original primary root zygote and separate zygote_next responsive is consistent with serving those requests; guest callers do not thereby gain access to their host app-start authority.

The installed switch is not an implementation of that policy: it stops zygote971, kills names995–999 and repeats service stops1011; return broadly kills system_server225. Deleting those commands preserves neither a semantic ingress filter nor private socket/data/property routes. Freezing the processes would also prevent the mandatory callback work. The first disqualifier is a design that requires all host forks/UI/AM workers to stop while it cannot provide the proven biometric bind and genuine policy/lifecycle routes. Where the real request cannot be classified or delivered under admitted physical/user/native ownership, guest admission stays closed; it is not permission to silently lose a security producer. No complete retained topology or shared-security case is accepted here.
