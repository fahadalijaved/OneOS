# Samsung LockSettings construction frontier

**Observed source:** cold construction can reconcile and delete recoverable-key state before Samsung LockSettings publishes either its local service or Binder. Supplying correct state after construction is too late. This report closes selected previously uninspected constructor callees; it does **not** close Stage 1's actual Context, state, native or lifecycle bindings.

All evidence is offline. No OEM class, service, JNI or phone operation ran. [The derived inventory](../inventory/construction-credentials.json) records 31 newly selected code bodies, 14 reused bodies, exact source PCs, body hashes, raw/reader receipts, 13 assertion groups and the remaining binding frontier. These counts describe evidence scope, not completion. [The authored driver](../tools/audit_credential_construction.py) regenerates metadata with `--report`; `--collect` reads only its bounded selectors through the shared DEX041 reader. Original credential/startup reports remain unchanged. Archive identities are the previously pinned Samsung services `def967fb…` and framework `8095a9ae…`; all logical headers are preserved.

PCs below are hexadecimal DEX code-unit offsets within the fully named method; the inventory supplies exact descriptors and raw evidence. The new framework bodies include `SemFloatingFeature`, `DualDarAuthUtils` and `VirtualLockUtils`, rather than inferring behavior from declarations.

## Newly closed synchronous cleanup path

`LockSettingsService(Injector)` reads `RecoverableKeyStoreManager.mInstance` at `0xbf` under the class monitor. Its `IF_NEZ` at `0xc1` skips cold creation to `0x17b`. The cold branch constructs a recoverable database helper, snapshot/session owners, separate PlatformKeyManager/ApplicationKeyStorage, CleanupManager and scheduled executor, then invokes the eleven-input manager constructor at `0x15f`. It stores the singleton only after that constructor returns (`0x162`). A warm singleton requires its original Context/database/native-owner provenance; resetting it is not a valid integration workaround.

The new manager constructor synchronously calls `CleanupManager.verifyKnownUsers()` at `0x1a`. This reads stored user serials and queries the real `UserManager.getSerialNumberForUser(UserHandle)` at `0x47`:

| Actual condition | Actual reconciliation |
| --- | --- |
| Live serial is `-1` | Removes that user's recoverable data at `0x56`. |
| Recorded serial is absent/`-1`, live serial exists | Stores the live serial at `0x66`. |
| Recorded serial differs from live serial | Removes that user's recoverable data at `0x79`, then stores the live serial at `0x80`. |
| Live and recorded serial agree | Skips removal. |

`removeDataForUser` removes in-memory snapshot entries, calls `File.delete` on snapshot files (`0x31`), invokes `ApplicationKeyStorage.deleteEntry` (`0x5b`), then issues SQL deletes against `keys`, `user_metadata`, `recovery_service_metadata` and `root_of_trust` (`0x95/0xa7/0xb9/0xcb`). ApplicationKeyStorage's selected deletion body reaches real `KeyStore.deleteEntry` (`0x1a`). `storeUserSerialNumber` updates `user_metadata` through `SQLiteDatabase.update` (`0x49`). These are conditional real mutations, not observation-only metadata reads.

The manager constructor catches `java.lang.Exception` from the `verifyKnownUsers` invocation (try start `0x1a`, length 3, handler `0x1e`), logs and continues constructing its AES key-generator owner. **Inference:** normal constructor return cannot certify successful reconciliation; an exception may follow partial external progress. Actual stored users, keys and runtime branch outcomes remain unknown.

**Required preconstruction binding:** authoritative user IDs **and serials**, the matching recoverable database/snapshots, correct default-loaded AndroidKeyStore identity and admitted maintenance transaction ownership. The state stream's [construction-state report](construction-state.md) traces OneOS staged `/data`, fresh `/metadata` and path resolution. Matching the integer user ID alone cannot satisfy this cleanup contract. Do not copy/reset records or expose a guest user list to authoritative data to make the constructor proceed.

## Publication and later active startup

Reused exact bodies establish this order: `Lifecycle.onStart` installs AndroidKeyStoreProvider; creates Injector/Context and LSS; LSS performs the effects above plus receiver registration, storage/SPM setup and concrete local-service lookups; LSS finally registers `LockSettingsInternal` at constructor PC `0x400`; only after constructor return does lifecycle publish `lock_settings` at `0x18`. The local and Binder publications occur after earlier external effects. There is no demonstrated constructor-failure unwind or standalone stop/drain contract in these selected methods.

`systemReady()` is separately active: it checks write permission; reads the secure-lock-screen feature; prepares Samsung logging; obtains actual DevicePolicyManager failed-attempt state; invokes database/SP-blob migration (`0x2f/0x32`), reconciles LSKF policy and can migrate SP/profile KeyStore namespaces (`0xaa/0xdc/0xea`). It waits for declared AIDL AuthSecret (`0x12b`), with actual HIDL fallback, updates provisioning observer state and can report setup completion. It prefetches storage, acquires feature-dependent FingerprintManager/FaceManager plus BiometricManager, reads concrete SecureLockDeviceService state and can apply StrongAuth flags to real users. Phase-520/550/1000 work is separately recorded in the reused lifecycle body and startup report; `systemReady` must not be substituted for those callbacks or treated as a passive query. The new startup stream owns the exact guest callsite/order.

## Stage-1 binding frontier

**Observed required inputs:** compatible canonical Binder/SystemService and private Samsung types; one LocalServices registry; real Context and application Context; correct effective Samsung resources/features and PackageManager; main Looper and Handler/executor owners; ActivityManager, NotificationManager, UserManager, mount IStorageManager, concrete StorageManagerInternalImpl, supervision/UserManagerInternal, DevicePolicyManager, SecureLockDeviceService and later biometric managers. The main constructor and boot bodies identify these edges. They do not authenticate the objects returned by a guest registry or Context.

**Missing actual bindings:** selected objects and user/serial/state provenance; native provider/namespace and JNI registration readiness; real Gatekeeper/Weaver/AuthSecret, storage/Knox/DAR identities and boot policy; exclusive state ownership before eager reconciliation; partial-construction cleanup and durable uncertain-progress recovery. The selected LSS/SPM static initializers do not load their native implementation themselves. Existing native/startup evidence must establish the registration/loading owner; absence of a load call here proves neither native availability nor impossibility.

**Inference for the candidate design:** establish the class/resource/Context realm and authoritative state/backend owners before first active construction; retain every started thread, receiver, executor and possible mutation obligation before publication; then drive the justified systemReady/phase/user order. Preserve one writer and actual recovery across switch/return. A null lookup or concrete cast alone is not proof of success or impossibility. These source facts narrow the required assembly; they do not select fake objects, demonstrate a runnable transplant or satisfy runtime acceptance.

## Smaller owner and adapted ColorOS alternative

Apple's current direction permits adapting ColorOS to Samsung and safely removing optional unsupported OPPO UI/features/background work. This audit does not turn those donor extras into mandatory Samsung construction dependencies. An original, unmodified LSS construction route carries the eager obligations documented above. A smaller coherent Samsung owner behind adapted genuine ColorOS clients is also a permitted candidate: it must identify its real construction route, retain the actual credential/SP/native/policy/key authority and account for every reached migration, cleanup, observer and recovery obligation. It cannot claim that omitting a constructor also omits its security responsibilities.

Neither the entire Samsung system_server nor every original LSS feature is proved minimal. For a narrower owner, explicitly classify optional facilities and their clients, prove that removed work is not required by reciprocal credential/fingerprint operations or intended app/key/data policy, and preserve a safe unavailable state and teardown. In particular, recoverable-key support cannot be silently dropped merely because its constructor cleanup is inconvenient; its actual consumers and required policy need a decision. No such extraction or feature removal is implemented by this source audit.
