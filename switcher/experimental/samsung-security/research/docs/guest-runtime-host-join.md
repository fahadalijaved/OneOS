## Why host Java spawn is not the privileged source

The actual host module's eligibility/control path checks `Process.myUid()==1000`. `gvi_open_existing` line206 explicitly refuses unless `getuid()==0 && geteuid()==0` and `one_thread` passes. GVO separately enforces a dedicated single-thread/sole-waiter profile and consistent real/effective/saved IDs. Loading GVI into the existing multithreaded SystemServer is therefore not a permitted shortcut. A child created by ProcessBuilder has no source API that grants root; an independently admitted set-ID/root-service transition would itself be the missing privileged producer. No such transition is inferred from executable bytes, a UID label or successful Java process creation.

The captured Samsung `core-oj.jar` and captured original donor copy are byte-identical (`be82060f…`). Exact Samsung-source reads show:

- `ProcessBuilder.start` invokes `ProcessImpl.start` at PC94 and wraps its IOException/IllegalArgumentException. This is a Java process-creation API, not a root service.
- `ProcessImpl.start` creates UNIXProcess at PC237, invokes its constructor at PC255, performs later redirect-stream cleanup and returns that same object at PC303. Default PIPE endpoints use the three standard-stream cells; this is not an SCM_RIGHTS/Binder-object transport contract.
- `UNIXProcess.<init>` invokes native `forkAndExec` at PC3, obtains its result at PC6 and stores private final `pid` at PC7. Only then does it allocate the privileged action at PC9/11 and invoke it at PC14. Its catch unwraps PrivilegedActionException as IOException; it does not supply the caller a partially constructed Process or an original-child cleanup acknowledgement.
- `initStreams` allocates/wraps three streams before submitting the process reaper at PC55–62. Its body has no cleanup handler. `waitFor` depends on the object's hasExited/exitcode state; `processExited` installs that state and notifies waiters. `destroy` requests native destruction and attempts stream closes; return is not whole process/descendant or native-resource drain.

Consequently `start()` throwing is **not proof that no native child was created**, and a wrapper that adopts only its returned Process misses post-fork construction/stream/reaper failures. No syscall or native forkAndExec implementation was executed or newly audited here; these source contours alone forbid the no-child inference. The exact returned Process can be useful on a normal return, but it neither elevates the caller nor closes the missing root session/callback edge. A new wrapper that merely records this fact would not advance the required privileged launch.

## One next implementation boundary: OneOS live root session creation

The single next boundary should be a **new, default-disabled retained-runtime launch operation in OneOS's actual root producer**, separate from legacy `LAUNCH`. Its contract is `beginOwnedRetainedRuntimeSession()` with no caller PID, namespace number, raw backend/context, arbitrary argv/environment or ready flag. This is an API change requirement, not an existing Java method or a fabricated root-service implementation.

The operation must actually enter the fixed first-party native root controller from the approved root path and create/retain a live native session before acknowledging it. It must not call the old takeover script, detach into `setsid … &`, return only `$!`/`@@OK`, or expose a pointer/FD/namespace scalar as authority. The native controller is the single-thread owner of the actual GVI/GVO instance, input descriptors, loop/control and exact child wait relationship. It stores each actual owner/resource before fallible acknowledgement. A code hash restricts the selected executable; the source-owned launch and actual live process/control callback establish the occurrence.

Concretely, OneOS must replace the selected root path's `Stdin.NONE`/detached text-completion API with a live session/control API. The initial native controller remains **admission closed**: it must not fork the guest or perform GVO view effects until the real source-owned control handoff is established. Java acquisition is marked uncertain before a potentially spawning call, with no retry/no-child claim on an exception. If the app/root bridge loses the constructor return, the native admission-closed process may still exist: lack of an attached permit is not reap. Any self-timeout can report only its own proven local closure; close uncertainty retains its owner/HOLD. This initial source-owned root-helper/control acquisition is part of the required OneOS API, not filled in with a supplied Boolean.

The current selected records do not contain that live root-service/process/callback API. This is the first concrete unclosed producer. Therefore do not implement a public `prepare(arbitraryProcess)` or a host-side launcher wrapper and call the join complete. Root must select/author the actual OneOS root launch/session provider first; the current shell command builder and pinned script are insufficient to manufacture it. This boundary advances real launch custody by replacing detached creation with an actual retained privileged native owner, rather than adding another private readiness record.
