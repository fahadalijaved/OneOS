# Genuine security-policy owner: load, updates and persistence

**Disposition: source/API frontier frozen; no policy provider selected or implemented.** Original policy data objects are a smaller starting point than full DPMS construction, but they are not an independent initialized authority. The selected original operations retain DPMS delegates, genuine package/admin and user/profile inputs, live observers, administrative effects and persistence. A staged counter, copied policy XML or hand-authored policy map cannot replace that ownership.

The [inventory](../inventory/security-policy-owner.json) contains exact descriptors, body hashes, decimal DEX PCs, direct caller scans and original R8 dispatch proofs. [The verifier](../tools/audit_security_policy_owner.py) checks the pinned inputs with `--report`: 79 code bodies, 17 assertion groups and five selected R8 cases. Counts describe static scope. [Frozen F](authority-bootstrap-policy.md) remains unchanged and supplies original data paths, parsers, cache/publication and constructor evidence. No private policy/user/credential files were read; no OEM, Android, Binder, native or phone operation ran. Installed state and whether any administrator/profile exists are unknown.

## Smallest observed original load frontier

`OwnersData.load` and original owner subparsers supply device-owner types and profile-owner records; `Owners.load` populates the actual DeviceStateCache. Required paths and original parser delegation are pinned in F. These are authoritative mutable records, not constants inferred from firmware or the absence of a PC-side file.

Per-user `DevicePolicyData.load` supplies failed counts, setup state and active-admin records from original `device_policies.xml`. `DeviceAdmins` owns its shared per-user data map and retains the real `Lock`, `Injector`, `Owners`, UserManager and **DPMS delegate** (constructor PC24). Its lazy `getUserData` invokes `initializePolicyDataFromXml` (29). That initialization loads actual policy, validates the password owner, updates maximum lock time and status-bar policy, and updates provisioning cache state. Calling the original loader is therefore an active policy operation.

Admin loading also resolves original package receiver metadata through `IPackageManager.getReceiverInfo`, checks `BIND_DEVICE_ADMIN`, then constructs original `DeviceAdminInfo`. Matching a component string or allocating an empty ActiveAdmin would omit this producer. Genuine package/user/permission/resources and the same current profile/challenge state remain prerequisites.

For the selected history operation, DPMS authorizes caller/cross-user access and aggregates the strictest applicable active-admin requirement. Its actual function reads `ActiveAdmin.passwordHistoryLength`. Profile aggregation includes genuine UserManager profiles and parent-active-admin relationships. The verifier follows original constructor discriminators: history lambda16 case9 enters PC132; credential-owner lambda8 case0 enters PC127. The latter uses real profile parent/credential-owner queries. An unrelated merged lambda case using DevicePolicyEngine is **not** automatically a dependency of that selected credential-owner call. Other operations and full DPMS bootstrap may independently require that engine.

## Samsung failure-count synchronization is a required adaptation

The original Samsung LPU failure path reads `ILockSettings.getFailureCount(user)` at PC40, then calls DPM `reportFailedPasswordAttemptWithFailureCount(user, count)` at 77. Exact register/data-flow checks establish that argument order. The guest LPU instead calls plain `reportFailedPasswordAttempt(user)` at 14.

Samsung LSS obtains that count through its original SPM and selected Hermes/Weaver or Gatekeeper path. It is neither the guest UI's count nor an arbitrary integer supplied by a new client. The DPM count-taking service stores the count at 66 and invokes its ordinary failure processing at 69. Ordinary processing consumes a positive synchronized count; otherwise it increments its policy count. It saves at 102, evaluates the real admin wipe threshold at 109, sends `ACTION_PASSWORD_FAILED` at 131 and can call `wipeDataNoLock` at 239. These are conditional source effects; none ran and no actual threshold/admin state is known.

Selected guest SystemUI direct callers are the Keyguard callback, authentication repository and biometric credential interactor (three failure callsites; two selected success callsites). Their real LPU reporting must reach the same original policy owner with Samsung count synchronization. Copying counts or merely redirecting a query to DPM would leave the update semantics split. Reporting/retrying twice can repeat state and admin effects. Trust reporting also has its original feature-gated path; the separately owned local LockSettings listener adaptation must not synthesize an additional LPU/DPM/Trust report.

## Shared history and credential-change completion

Both selected native Settings password fragments call genuine `checkPasswordHistory`. That check reads `lockscreen.passwordhistory`, actual salt and the supplied real hash factor, then uses DPM's requested history length. Samsung LSS's original post-change path reads that same policy requirement and updates the authoritative history key. Redirecting only the length getter while retaining guest LSS history/salt state is insufficient. Credential/hash-factor transport remains under the actual typed LockSettings endpoint work; this card creates no secret copies or replacement history store.

Original LSS `notifyPasswordMetricsChanged` posts real captured PasswordMetrics/user work. Its original lambda3 branches call DPM `reportPasswordChanged` at 17/33; one also reports to WindowManagerInternal. That queued policy tail must belong to the credential transaction and drain before handoff. It must not run once against host policy and again against a staged guest policy. Exact old-owner queue/drain work remains in the quiescence stream.

SecureLockDevice has a separate persistence gap: `updateStateAndWriteToFile` changes memory enabled/client fields at 16/18, then posts the original writer at 33. The writer later reads those fields under its original lock and calls `saveToFile` at 13. Operation return or enabled-status notification does not certify that queued write committed. Preserve the original queued owner, error outcome and real write-completion boundary; no invented ready flag or presumed rollback closes it.

## Source/API decision boundary

The existing typed operations and exact producers above are the reviewable boundary. Either retain a coherently initialized original policy family, or first close an extraction that retains its actual loaded data, delegate behavior, permissions, profiles, admin effects, live updates and persistence. This report creates neither an interface nor a runtime wrapper as a substitute for that closure.

Before selecting either route, bind authoritative state and actual users/package metadata before lazy loading or cleanup; route guest failure/success/history/change callers to that same owner; retain original Supervision/SecureLockDevice policy and completion; and establish one writer plus real update/queue/write completion and uncertain-progress reconciliation. Original policy, required additional-factor behavior, ordinary old-PIN rejection and genuine Samsung prior-credential recovery remain intact. Unknown private state is not an unmanaged/feature-off policy. No provider implementation, firmware selection or device candidate is approved by this source card.
