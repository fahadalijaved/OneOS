## Why the restricted registry proposal still is not full user ownership

The previous registry card already closes the specific query counterexample: public `getProfileIds(String,int,boolean,boolean)` reads Persona24, dereferences it26 and uses genuine `workTabSupportLauncherUids`29. Its real producer queries launcher package metadata/UIDs and refreshes asynchronously. Null Persona or an invented empty launcher list cannot supply that required profile behavior. The prior four retarget proposals were source/API preparation for a bounded registry/query owner, not a full executable user service.

The independent [lifecycle card](samsung-user-registry-lifecycle.md) supplies the next concrete boundary. Real guest UserController obtains/casts a **concrete guest UMS**, then calls `onBeforeUnlockUser` before committing UMI state2. The actual Samsung existing-user method invokes UserDataPreparer43; its ordinary nonmanaged branch53→132 also reaches concrete Samsung `StorageManagerService.StorageManagerInternalImpl`, parent SMS lock/prepared-user set132–163, then PMInternal package-data reconciliation185/189. This is not merely an optional DualDAR branch. An original-vold invoker supplies neither this Java storage-preparation owner nor package-data policy. The new peer receipt/raw/body pins are independently verified by this auditor; no additional collection was needed for this edge.

Consequently a map-only UMI control can neither replace those concrete guest calls nor prove their pre/post ordering, user/serial/CE subject or stop/lock/drain semantics. Conversely, these source facts do not prove that all PMS/SMS/AM functions are necessary: a future source-preserving extraction could retain the actual selected responsibilities. None is implemented or admitted here.

## Disposition and one next engineering action

For an **unchanged** cold path, the earliest missing owner is genuine PMS/custom-injector at254, with the wrong Context-only state root also unresolved. Choosing the production factory moves that requirement upstream: real PMS/Installer/locks/Persona/local package owners and their active construction are required before UMS load. Choosing the documented narrow retargets instead leaves physical writer/recovery, publication failure, Persona policy and the concrete UserDataPreparer/SMS/PMInternal lifecycle responsibilities unbound. Neither route is an executable owner contract for all required outcomes. No new cold patch leaf is recommended.

The bounded alternative is to retain the **same initialized original UMS/UMI/PMS/Persona/UserDataPreparer/SMS cohort** in its original live process and physical/configuration view, preserving its real policy and queued work. `UMS.getInstance()` reads the actual singleton; PMS retains `mUserManager`; UMI is the exact LocalService tied to that UMS. They are source-owned object relationships for an admitted same-process hook, not remote object transfer, name matching or arbitrary Binder attestation. All six retention topology gates, original active producer exclusion, guest package-data separation, callbacks/native/persistence drain and safe return remain required.
