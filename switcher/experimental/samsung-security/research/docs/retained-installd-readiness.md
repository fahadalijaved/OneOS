# Samsung installd startup and guest acquisition

Samsung's native publication precedes its isolation-cache initialization. The first source edge that preserves the original initialization order and can acknowledge both is the successful return from `InstalldNativeService::start()` in the same process's original `main`. The existing guest alias and filesystem owner have no such producer. The proposed barrier keeps the retained Samsung daemon and its callers on their existing canonical route. The new barrier applies to the separately owned guest daemon and guest ingress.

## Exact producer

These are ELF virtual addresses in the captured Samsung installd `ed618c38…`. The [inventory](../inventory/retained-installd-readiness.json) joins the saved decoding to all instruction bytes in the three relevant native functions. The [native owner audit](retained-installd-native-owner.md) supplies the original capture and pre-publication path provenance.

| Address | Actual original edge |
| --- | --- |
| `0x8b070`, `0x8b090` | `main` can write the real layout version before calling `start()`. Layout, user-config and conditional migration work can occur before a refusal. |
| `0x2622c`, `0x26238`, `0x26348` | Acquire the original manager, select the literal `installd`, and call the manager's publication slot with the real constructed native Binder, `w3=0` and `w4=8`. |
| `0x26390`, `0x263a4`, `0x263ac` | The nonzero publication status bypasses the success path. The zero path starts Binder workers and names the pool. |
| `0x263d8`, `0x263e8`, `0x263f8` | Call the original `GetBoolProperty("persist.zygote.app_data_isolation", true)`, reduce the returned value to a bit and release-store it at ELF address `0x98334`. Both Boolean values can be genuine results. |
| `0x8b094`, `0x8b098`, `0x8b0a0` | `main` branches away on nonzero `start()` status. The success fallthrough at `0x8b098` leads to `joinThreadPool`. This is the proposed in-process acknowledgement location. |

`tryMountDataMirror` acquire-loads that same byte at `0x3f958`. A zero goes through `0x3f95c` to `binder::Status::ok()` at `0x3fa44`, bypassing mount work on that branch. The address is in `.bss` and the consumer has no separate initialized bit on this path. A zero branch and an OK reply therefore cannot certify that the original property read/store happened. This is a control-flow result. No startup race or initial byte was observed at runtime. A fresh read of the property would likewise be a different read and cannot establish the original cached value or its initialization.

## Actual clients

| --- | --- |
| Samsung services | `Installer.connect` looks up canonical `installd` at PC 3, links death at 21, adapts the Binder at 28, stores `mInstalld` at 32 and releases the latch at 36. | Acquired OneOS staged services `efb45f5f…` | `Installer.connect` looks up the same logical name at PC 3, links death at 15, wraps it with `OneOSInstalldProxy.asInterface` at 23, stores at 27 and releases the latch at 31. The [host routing audit](retained-installd-routing.md) and [staged lifecycle audit](retained-guest-user-lifecycle.md) supply the client bodies. The staged archive was acquired and identified statically. No loaded guest instance or client behavior was observed. The latch acknowledges Java handle publication. A manager lookup, registration callback, PID observation, transport ping or ordinary successful RPC has no demonstrated causal dependency on the release-store above. The [publisher-only alias](guest-installd-alias.md) changes the name operand and preserves the original ordering.

## Proposed barrier

1. **Keep admission closed before native birth.** The actual private-view owner must create and retain the single guest launch occurrence, its process identity, sole waiter and child-specific control channel before exec. Supply its reviewed code/loader, property, filesystem and caller profile before the first native effect. Keep guest code that can acquire the endpoint stopped until the barrier. Current GVI/GVO can hold the partial filesystem view, and its public API has no daemon-exec transition. [Launch inputs](guest-native-launch-profile.md) · [Property owner](retained-property-view-plan.md)
2. **Acknowledge from the original success path.** Preserve the original startup and property-read order. An authored hook on the `0x8b098` success edge may send one complete startup record on a dedicated inherited message channel after the original cache store and `start()` return. Only the selected daemon image may inherit the send end, and its supervisor retains the receive end. Tie the record to the supervisor's one launch occurrence, preserve original failure branches and reach original pool join on the successful path. A lost or partial record, an expired deadline, a dead child or an ambiguous send leaves ingress closed and retains the actual process and view for retirement. A parsed record acknowledges the selected startup phase only.
3. **Pair the startup occurrence with the actual endpoint.** Bind acquisition to the same Binder passed to the actual publication call. One possible producer retains that exact native Binder before the original local strong-reference release and supplies it over a source-owned Binder bootstrap. A second possible producer is an actual manager-owned exclusive guest slot that binds the publisher occurrence to the acquired handle and excludes replacement through admission. No such slot or Bootstrap producer is selected. An inherited socket record can carry startup evidence, and Binder transfer still requires Binder. Matching a string, PID or descriptor cannot substitute for this join.
4. **Release the guest acquisition gate before the first logical lookup.** Gate the selected guest process or all of its relevant initial and reconnect acquisitions before the first `Installer.connect` lookup at PC 3. Use the admitted endpoint through the original proxy, death registration and genuine method/error semantics. Bind native lookup/wait/notification and any bootstrap cache seeds that can bypass that Java call to the same route. On endpoint death, mismatch, stale cache or a queued reconnect, keep guest admission closed and retire the failed occurrence. There is no fallback to canonical host `installd`, handle swap or automatic restart on ambiguity. Keep host calls running on their retained authority. [Guest manager seam](guest-service-namespace-preparation.md)

That hook preserves registration before property sampling, so it can only be used with demonstrated exclusion of early guest calls. If that exclusion cannot be supplied, the safer source placement is to perform the original cache initialization before publishing the guest alias. Such a successor would deliberately change the sampling order and needs its own binary/source, failure-path and exact Binder acquisition proof. Moving only thread-pool startup or adding another readiness bit to the Java client leaves the already-visible native publisher unresolved.

The smallest next artifact is a reviewed guest-only producer at the original success edge plus an actual way to pair its published Binder with the first guest acquisition. The current evidence gives an exact insertion point, and the local alias patch supplies neither instrumentation nor endpoint issuance. An isolated source fixture could discriminate ordering and failure handling after those producers exist. A fixture with stand-in readiness flags would test a new protocol's model and could not establish the original edge.

## Static verification

`python -I -B tools/audit_retained_installd_readiness.py` reads the ten pinned inputs, rejoins the three native bodies to the captured ELF, and checks five exact client body records. It emits the [static inventory](../inventory/retained-installd-readiness.json) to stdout. The check passed offline. Startup, the cached runtime value, Binder identity, guest launch and native drain remain unproved.
