# First retained-capture test: bounded independent review

**Recommendation:** prefer a minimal Registry-v2 + Family successor for the next useful observation. A no-restart single main-thread task is conditionally feasible, but actual delivery into the already-running SystemServer remains unproved. If that delivery cannot be established, a separately reviewed combined one-restart proposal is more informative than deliberately spending a restart on Registry-only capture first. Root selects the artifact and procedure; nothing here authorizes a build or phone action.

## Existing v1 still has a useful, narrower result

The signed 21,104-byte APK `bb0eba10…` contains Module, PermitFile and the actual Registry-v1 pair (`26fcbb30…` source). Its normal-return phase1000 hook tests real Vector installation/delivery, main-thread/profile/permit admission, service-loader/TCCL compatibility, reflection access and the Registry's existing local-root relationships. This is materially useful if that common ingress is the question being diagnosed.

It does not capture the actual LSS/StrongAuth/SPM/storage and fingerprint/Biometric/Auth family. A Registry-only success would still leave those distinctive owner relationships, six field-access exceptions and the original credential monitor untested. Running v1 is therefore not a prerequisite imposed by the reviewed components. Its current code only observes a future phase1000 normal return: a late-installed hook has no backfill and may never attempt capture in that process.

The proposal's operational prerequisites are still unselected: actual normal soft-restart method, bounded observable result channel, source/profile/permit preflight and exact fresh approval. Detail's newly supplied Vector log-source finding reports INFO suppression when `u1.b` is true; the current module always logs INFO. This review treats that finding as peer evidence, not a new completed log audit. Silence would remain inconclusive; the existing APK must not be run on an assumption that its fixed codes are observable.

## Minimal combined successor

The reviewed actual Registry-v2 and Family SDK classes already passed their separate authored runs: receipts `52068829…` and `e2bf02e8…`. A combined APK must replace the old Registry pair with actual v2 `8c23983a…` / `096443d1…`, and package actual Family `dcf55c45…` / `963c3e94…`. Appending Family to the old v1 package is incorrect: v1 lacks the compare-only method the Family calls. With Module/PermitFile this is exactly six authored definitions, with Registry and Family in the same defining loader/runtime package; no duplicate Registry, OEM/model definitions or extra loader is needed.

Adopt and retain Registry immediately after its factory returns, report its fixed stage independently, then capture/adopt Family before its subsequent check/log. A Family refusal must preserve the successful Registry owner/result rather than collapse both into an unexplained common failure. Keep one attempt, bounded fixed codes, default-off permit and process-lifetime retention; no retry, polling, unhook or destruction is established.

Family adds metadata access, a bounded ArrayList scan and three reads under the actual `mUserCreationAndRemovalLock`. It adds no credential operation, provider/HAL call, service construction or native-auth action. It is nevertheless additional SystemServer-main work: acquiring that original monitor can block, and ART access/real graph relationships remain untested. The combined artifact/procedure needs its own source/packaging/exception-containment review and approval; the old v1 marker/proposal must not silently be reinterpreted as permission for broader capture.

## Conditional no-restart alternative

Registry requires the actual original `isBootCompleted()` result; Family additionally checks phase at least1000. Both require the existing original graph on the genuine main thread, rather than a new boot-phase transition. A successor could receive a genuinely late module callback and submit exactly one task to a Handler using the existing main Looper, with no hook or new Looper. Recheck profile, permit, genuine TCCL/loader and capture predicates in the task; never coerce TCCL to make them pass. Retain Handler/task ownership before posting, as the task can finish on main before a foreign posting thread returns. Queue acceptance is not capture completion; a late QUEUED assignment must not overwrite a completed result. Refusal/uncertain posting must not cause retry, and queued work/owners remain retained.

The saved Vector bodies prove direct callback invocation in `t2.c` at PC26 and late dispatch in `u1.b` at PC514. They do not prove that callback runs on main, or that enabling a new module delivers it into an already-running SystemServer. The shared author independently confirms that gap. Current `autoHotReload=false` and `onHotReloading=false` also mean a same-package update must not be presumed to replace v1 classes already loaded in that process. Fresh process/package-state preflight and an actual selected delivery strategy are required. Handler posting addresses thread placement only; it does not create delivery or replace old classes. Early execution before boot readiness must refuse without replay/polling. A selected existing-process delivery route and observable fixed-code channel are blocking prerequisites for a no-restart proposal.

Either result remains immediate object-binding evidence only: no user generation, native custody, policy readiness, lifetime/drain, credential/CE/app-key acceptance or switch survival. All18 full-goal device cases remain pending. This review performed only source/saved-metadata reads and hashing, with no source change, build, model replay or phone action.
