# Batch 2 independent adaptation/coherence review

Status: final bounded PC adaptation/source checkpoint review. GOAL governs;
optional unsupported OPPO work may be removed, while full reciprocal Samsung-
controlled PIN/fingerprint, policy, app-key/CE and recovery behavior remains
required. No runtime is selected. No OEM, phone, installation or Git action was
performed by this reviewer.

## Two different acceptance questions

An optional, unselected code leaf can be accepted when its exact original
inputs, limited removal semantics, preserved required behavior, inverse and
validation limits are reviewable. It need not assemble the entire Samsung
runtime first. That acceptance must not imply live removal/drain, actual ART or
APK/JAR signing, installed-image identity, hardware behavior or a phone candidate.

Runtime selection is separate. It needs genuine current authority/user/policy,
the correct constructor/state/native owners, original transaction semantics,
caller admission, readiness and return/drain. A leaf's missing selection
conditions remain explicit; do not fill them with success, NONE, zero lockout,
fake flags, an assumed callback acknowledgement or a cached foreign generation.

Cold-only is a legitimate selection restriction for an unselected leaf. Define
which process, class initialization and authority generation it assumes. A future
fresh process can prevent its own registration; it does not prove a previous
process, remote callback or native session has drained. Conversely, do not demand
that a cold-source leaf implement a live hot-swap it does not advertise.

## Composition must preserve the reviewed cuts

Root owns integration. Require exact immutable base identity, exact changed
methods/code ranges, target class/DEX ownership, source method hashes and each
leaf's conditions. Disjoint names alone are not proof of disjoint byte edits.
For overlapping archive/DEX inputs, compose admitted slices against the same
base, revalidate final branches/tries/code ownership and integrity, and preserve
an exact inverse to that base. A producer pinned to the original must not silently
consume another leaf's output or a moving receipt as its own source.

The final combined receipt must retain the strongest selection conditions of all
leaves, not only their common subset: cold-only, optional consumer exclusion,
required cache/policy/caller ownership and installed-profile requirements. Record
what actually ran. Positive source/header/checksum/inverse checks do not imply
actual-byte malformed branch/try/alias negatives, Android verification or failure
tests. Existing decoded-record negatives remain labeled as such.

## Smallest genuine backend choice to settle

**Inference from the existing construction evidence:** keep guest-specific app/
volume ownership separate and adapt ColorOS callers to a narrow Samsung-facing
credential/policy/biometric contract, using genuine Samsung state/native owners.
Do not import optional OPPO RPMB/RoR solely to satisfy a caller that can safely be
removed. Do not import full Samsung storage startup solely to satisfy a concrete
inner-class cast if an exact policy-preserving typed retarget can close it.

This is a candidate cut, not a runnable minimal backend. The decisive unresolved
choice is whether actual selected Samsung credential/SP/policy owners and native
helper registrations can be constructed coherently in the guest realm, or need
a separately owned Samsung authority realm. Both still need original user/serial,
state and native endpoint ownership before initialization. Retaining existing
host Java objects is a third, distinct proposal: current OneOS stops that process;
surviving native Gatekeeper/Keystore daemons do not make its LSS objects survive.

The narrow backend must cover real final verification/change outcomes, original
strong-auth/additional-factor and lockout state, existing fingerprint/session
policy, actual key/CE effects and uncertain-commit reconciliation. A primitive
Gatekeeper verify call, native SID parser or Boolean broker alone is not that
backend. New JNI and Context evidence should resolve the next exact binding
frontier instead of defaulting to a whole framework import or claiming a tiny
broker already exists.

## Frozen component review

**Disposition: accept the four named leaves as bounded, conditional, unselected
PC components.** No blocking source-semantic defect was found within their stated
cuts. This is not acceptance of a complete feature removal, selected composition,
protected recovery or runtime authority.

* **Input/RPMB leaf:** twelve optional `setEntry` callsites and both getter/task
  producers are in scope. Both callbacks retain their original null task write,
  credential cleanup and original guard conditions. Existing family/minors
  lifetime behavior is not claimed repaired. The unchanged downstream null-task
  guard does not prove that realizing the manager is inert; separate RoR work
  and fresh-owner conditions remain required.
* **RoR leaf:** optional allocations/registration, initial recovery calls, common
  destinations and dedicated callbacks are disabled. Independently reread the
  selected constructor tail: only RETURN_VOID follows its allocation cut, so no
  deleted temporary feeds later constructor work. Original mandatory monitor
  registration, handler101, policy and genuine finish methods remain. The
  untouched handleKeyguardDone source calls setIsSystemRebooted(false), whose
  original preference updates include the reboot/need-verify flags. The peer's
  real exit callback supplies that route; optional recovery callbacks are not
  the only source path for clearing it. This resolves a suspected source blocker,
  not proof that Samsung-backed runtime finish or UI readiness works. No startup
  fake finish/clear is permitted.
* **Settings leaf:** the exact prefix removes optional private RPMB invocation
  and its immediate unconditional success diagnostic. The retained mixed tail
  still owns old-retrieval/modification-record work and captured credentials/
  Intent/worker. It neither releases those owners nor completes wider optional
  retrieval/cache removal. Real set/verify/remove/enrollment code is outside the
  cut. Its structural actual-byte negative fixtures are distinguished from
  runtime tests, complete malformed-DEX coverage and the other leaves' negatives.
* **Readiness leaf:** throwing the original caught exception after the original
  log removes two new error-to-NONE/ZERO recomputations. Normal legitimate results
  are preserved. Cached hits, authority/user generation, policy application,
  protected unknown presentation and owned recovery are still absent. An
  exception/crash is not completed fail-closed mode or safe return. Accept the
  error-propagation cut only, not a working readiness owner.

RoR source support/capability properties and every optional UI are not themselves
made unavailable by the two SystemUI leaves. Broader integration must close those
entry points and disclose unavailability; the component claims cannot become
"all OPPO feature removal complete." Removing the SP callback also removes its
incidental cache invalidation, which must come from genuine committed changes
for the current user/generation before consumers resume.

Settings expresses its cold/capture/cache restrictions in selectionConditions
and its status text, without the common coldStartOnly/requiredSelectionConditions
fields. A future general composer must retain those conditions rather than treat
missing common fields as permission. The current SystemUI pair shares the common
schema; root owns any other composition.

## Coherence checks and native/user backend narrowing

This reviewer compared the frozen SystemUI metadata: same literal original APK,
14 input-leaf methods versus nine RoR methods, no common changed method and no
cross-leaf overlapping instruction range. This is metadata/source consistency,
not an independent final-composed-byte or all-method semantic proof. Builds and
large whole-archive/Java verification were not rerun by this reviewer. Component
proofs retain actual DEX039 signatures/checksums, source/body pins, inverse and
ZIP/signing limits. Decoded-record negatives, Settings structural byte negatives
and unexecuted malformed-byte/runtime cases remain separate evidence classes.

The source-reviewed native result narrows the next backend implementation:
canonical Scrypt's selected Java/JNI and normalized native paths agree; the
116-byte SID function is identical and reads offset1 through JNI critical array
access, not hardware. These facts do not require Samsung's entire native server
library for those helpers. They also do not bind a private imported SPM: the
actual registrar resolves its canonical Class, and the guest wrapper is protected
instance work, not a public static service. Choose deliberate canonical placement
or a scoped, source-preserving callable SID seam. Do not instantiate another guest
SPM just to obtain a receiver, treat an arbitrary parsed value as an authoritative
user/SID claim, substitute getSecureUserId or call a parser a credential authority.
The public format utility itself can process synthetic arrays without granting
authority. Native length/
version validation and transitive crypto/live linker equivalence are not proved.

The user-binding result likewise supports a genuine UserManager client plus
narrow typed operations instead of constructing another UserManagerService just
to query serials. The pre-cleanup route uses application Context before LSS's
later own user-manager field. Eleven matching remote codes do not make typed
UserInfo interoperable: Samsung has attributes in a sixteenth field and additional
policy consumers. Scalar serial transport is narrower; lists/records need explicit
semantic conversion. Local main-admin/shareability/supervision/maintenance and
current lifecycle policy remain separate genuine owners. A real surviving server,
not a client constructor or host snapshot, must back them after OneOS stops host
system_server.

Thus the smallest **source-supported next cut**, still not a runnable minimum,
is a narrow genuine Samsung credential/policy/biometric authority with verified
canonical crypto helpers/scoped SID adaptation, typed user/local-policy projections
and the already required storage port. Guest app/volume ownership stays separate.
These results remove specific whole-library/whole-user-service assumptions;
they do not select process placement or complete the real state/native authority.
