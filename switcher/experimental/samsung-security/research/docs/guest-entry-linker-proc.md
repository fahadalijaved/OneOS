# Guest entry linker configuration and procfs

The guarded private view lacks the linker configuration needed to select a guest launch. The cached donor root contains an empty `/linkerconfig` mountpoint. Its init source prepares a bootstrap profile and runs the APEX configuration step again after activation. The held legacy script instead imports the host's effective mount. The bounded precondition for the guarded child is to retain and verify the actual effective loader configuration for the exact selected executable, interpreter and APEX/partition view before permitting the first guest exec. None of the pinned inputs supplies that configuration today. [Byte pins and source assertions](../inventory/guest-entry-linker-proc.json)

## What the held legacy source does

The installed 0.4.57 capture of `oneos_switch.sh` runs `guest_prepare.sh` at line 1087, before the `unshare -m` launch of `guest_start.sh` at 1418. Preparation compares its mount-namespace link with visible PID 1 at 7–10. It creates the staged target directories at 292–295 and tries to mount procfs at `$ROOTFS/proc` at 297 if a text search sees no existing mount. It uses the current PID namespace. It recursively binds host `/linkerconfig` at 327, applies best-effort `rslave` at 328 and later attempts recursive privatization at 4305. These operations affect mount propagation, while the bind continues to reference the host backing files. They happen before the later private child starts.

`guest_start.sh` makes the inherited mount tree recursively private and pivots at 13–22. It attempts another procfs mount at 31 without testing its return, then requires the `/dev/null` bind over `/proc/sysrq-trigger` at 34–38. It detaches the old root and checks for surviving `/postinstall` mounts at 44–48. It never establishes a separate PID namespace. The script intentionally uses host process visibility later. At 191 it reads a previously identified host process's `/proc/$FZ/comm` and signals that process. The loop at 242–245 also finds and kills host SurfaceFlinger by name. That behavior cannot be assumed in a new PID namespace and must stay out of a guarded entry path.

The saved Samsung init mount table corroborates the source distinction. Its `/proc` row is shared procfs with `gid=3009,hidepid=invisible`. A tmpfs mounts at `/linkerconfig`, then its `/default` subtree covers the same path in a second row. Those rows do not supply the mounted files or attest the current live namespace. ## What the donor cache establishes

The cached extracted root has two ordinary empty directories at `proc` and `linkerconfig`. Donor `system/etc/init/hw/init.rc` lines 120–140 create `/linkerconfig/bootstrap` and `/linkerconfig/default`, write `#` placeholders and recursively bind the bootstrap directory to the active name. `exec_start apexd-bootstrap` and `perform_apex_config` follow at 156–157. The later path waits for `apexd.status=activated` and the KeyMint module hash signal before `perform_apex_config` at 1659–1663. The placeholders belong to an early boot stage. They are insufficient evidence for the eventual guest loader profile.

The cached donor runtime APEX's `linker64` ELF contains `/linkerconfig/ld.config.txt`, `/system/etc/ld.config.txt` and `/proc/self/fd/%d`. The matching `linkerconfig` ELF names `linker.config.pb` under system, system_ext, product and vendor. These are static byte observations, not a trace of which fallback the loader takes. The actual donor root has a 1,207-byte system protobuf and a zero-byte product protobuf. Its OPPO `ld.config.oplus.txt` is a different file under `/system_ext/oplusex`, with OPPO partition and library-list paths. None of these is the generated effective `/linkerconfig` tree. Donor init also creates its stdio symlinks against `/proc/self/fd/0`, `1` and `2` at 207–209. These entries require a real proc view when that environment is used.

## Bounded precondition and ownership

1. **Require an owned effective linker view before exec.** Add a closed check inside the existing child after it retains its actual private root and before any selected executable runs. It should accept only the genuine configuration for the admitted loader/APEX/partition combination. Resolve its paths in that root and hold the verified objects through exec and retirement. A feasible placement is an immutable, child-owned snapshot mounted read-only over the real donor target. Refuse the empty root, bootstrap placeholders, ambiguous stacked target, changed contents, or an absent configuration producer. A future profile borrowing host-generated bytes would need to prove that those exact files resolve against the same admitted dependency view. A host path or a copy of its directory alone cannot establish that equivalence.
2. **Choose and verify procfs separately.** A checked fresh mount under the owned root can support a deliberately shared PID view. Record the actual PID-namespace association and effective proc options, and make the required write restrictions and sysrq cover part of the selected profile. Verify the procfs type and actual mount/object identity after each attachment. A mount-only unshare cannot promise process isolation or turn kernel-global controls into guest-owned settings. If isolated PIDs are required, the actual child must enter the selected PID namespace before creating its proc view. That choice also needs its own PID 1/reap and host process-control route. It cannot reuse legacy name-based host kills. Keep host `/proc` available to the existing controller's own bookkeeping in its own context. Do not export it as a guest path.

The actual private-view owner uses `unshare(CLONE_NEWNS)` and checks its mount namespace at lines 599–603. It uses inherited `/proc/self` to validate descriptors and the child mount table. Its result at 722–737 is a partial filesystem observation. Neither `/proc` nor `/linkerconfig` has a guest-root graft in that implementation. The proposed precondition belongs to a future entry operation in that same owned child lifetime. No native or OEM binaries, scripts, mount operations or device work ran for this report.
