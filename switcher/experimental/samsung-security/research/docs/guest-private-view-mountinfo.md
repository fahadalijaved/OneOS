# Portable private-view mount metadata parser

`compat/native/guest_private_view_mountinfo.{h,c}` is a first-party C99 grammar component for the separately owned private-view preparer. It has no Linux headers, allocator, file/FD read, mount, namespace, process, signal or other OS operation. Caller-owned copied rows eliminate input-buffer lifetime coupling. Successful parsing does not authenticate text or admit a namespace, mount, image, descriptor, peer group or data view.

The header was agreed with Build and root before implementation. Build owns the Linux acquisition/resource owner; Power owns the separate host-native grammar driver/compiler receipt. The source passed independent review and the separately authorized host run passed 228 authored grammar checks; saved-output readback passed without replay. This report records that component evidence and measured saved-input bounds. No owner, kernel, Android/OEM or phone execution is selected by this component.

## Contract

- `gpv_parse_mountinfo(bytes,length,rows,capacity,&count)` returns `GPV_OK`(0), `GPV_INVALID`(-1) or `GPV_LIMIT`(-2). Failure sets count 0; rows are not a published partial table and must not be used. All input/output storage must be valid and non-overlapping, including input/rows/count and fdinfo/id. Input is immutable during parsing and consists of exact bytes, excluding any caller's terminal NUL, with final LF. The table and each field are copied without truncation.
- Row fields preserve positive mount/parent IDs; major/minor device numbers; decoded absolute root/mountpoint and decoded source; decoded filesystem type; encoded comma-separated mount/super options; shared, master and propagate-from IDs, and unbindable. No path normalization or filesystem observation occurs.
- Decimal overflow, bad field counts/delimiters, missing terminal LF, empty rows, raw control/NUL bytes, invalid/truncated escapes, duplicate mount IDs, duplicate propagation tags, unknown optional tags, zero propagation IDs and conflicting unbindable state are refused. Duplicate encoded option keys or conflicting ro/rw in either option set are refused; options are an opaque preserved lexical set, not parsed into filesystem capabilities. Unknown optional tags are unsupported, deliberately failing closed rather than guessed away.
- The admitted kernel root/point escapes are `\040`, `\011`, `\012`, `\134`; source and filesystem-type mangle additionally supports `\043` for hash. Encoded options also admit `\054` for comma, preserving it as part of the option rather than a delimiter. Decoding occurs once. NUL/slash aliases or arbitrary octal are not accepted. Encoded options retain their representation after escape validation. Raw path control bytes outside this strict profile are unsupported, even where Linux filenames may otherwise allow them.
- Shared-plus-slave **is legal grammar**: both shared and master survive parsing. Propagate-from requires a master; unbindable cannot coexist with those propagation tags. Rejecting a particular host master/group is the resource owner's separate policy.
- Equal decoded mountpoints with **distinct IDs are legal**, including stacked/overmounted paths. `gpv_mount_by_id(rows,count,actual_fd_mnt_id)` returns the unique row or NULL; `gpv_mount_path_count` reports only multiplicity and never selects a winning row. Neither row order nor pathname is an ownership rule. Returned row pointers borrow the caller-owned unchanged table lifetime; they confer no FD/resource ownership.
- `gpv_parse_fdinfo_mnt_id(bytes,length,&id)` extracts exactly one positive decimal `mnt_id`, rejects duplicate/overflow/malformed ID or framing and returns ID 0 on refusal. Other printable colon-labelled fields are not interpreted as capabilities. This is a directory/O_PATH baseline-profile mount-ID extractor, not validation of every filesystem-specific fdinfo field; whitespace-bearing unknown keys such as some timerfd/fanotify fields are unsupported. An owner must acquire fdinfo for the actual held FD and match it to the contemporaneous table; descriptor numbers supplied as text have no custody.

The hard profile limits are 2 MiB mountinfo, 4096 rows, 8192 bytes per row and 8192 bytes fdinfo; decoded root/point/source at most 1023 bytes each, filesystem type 63 bytes, and each encoded options field 512 bytes. Row capacity is bounded, all copies are checked, and no fallback truncation exists. Row storage is roughly 17 MiB at maximum capacity; the owner must allocate it outside the stack and release it when current readback is done, retaining only required scalar observations. This parser owns no persistent global table. The field-specific escapes follow the original [kernel mountinfo producer](https://github.com/torvalds/linux/blob/v6.6/fs/proc_namespace.c). One valid-kernel form is deliberately unsupported: [seq_show_option](https://github.com/torvalds/linux/blob/v6.6/include/linux/seq_file.h) can encode an equals sign in an option NAME as `\075`; this parser refuses that escape. Unknown optional fields and longer values are also conservatively refused. This strict supported profile is distinct from an all-version general-purpose mount utility.

## Why FD membership matters

The Linux kernel's [proc documentation](https://docs.kernel.org/filesystems/proc.html) defines per-mount IDs and fdinfo mount IDs. Its original [fdinfo producer](https://github.com/torvalds/linux/blob/master/fs/proc/fd.c) obtains the latter from the opened file's `f_path.mnt`. Consequently, an FD held across a bind can continue identifying the old mount while a newly opened target FD identifies a new mount, even when visible path/device/inode observations overlap. The parser preserves both rows/IDs; this architectural inference is not a test of a real bind. Mount IDs can be reused after unmount, so the actual owner must retain appropriate descriptors and current acquisition/lifetime checks.

The [shared-subtree documentation](https://docs.kernel.org/filesystems/sharedsubtree.html) distinguishes shared, slave, private and unbindable propagation. Parser output exposes those fields; fresh-peer and forbidden-parent-group admission must use the owner's actual saved host groups and post-operation FD membership/readback. No field, fixture string or successful lookup proves isolation.
