**Decision: the unchanged installed OneOS takeover cannot support this topology. A source-preserving retained variant is not disproved, but its physical display/input withdrawal and real keyguard-policy ingress are not yet implementable from the existing evidence.** Keep this architecture unselected. The next work is the two finite owner cuts below, not another broad security graph or a raw locked-state setter. No phone/OEM execution, activation, patch, new body query or runtime interface was performed.

This plan uses the acquired installed code74 APK/profile and saved original Samsung bodies. It does not substitute the older0.4.55 source or equate installed0.4.57 with a Git commit. ## Actual physical ownership conflict

The installed switch stops host zygotes971/979, optionally stops host SurfaceFlinger985, kills name-selected app_process/zygotes/system_server995–999, and installs the recurring stop keeper1011. Guest-start then kills the retained splash SF190–194, restarts the actual composer215, stops/kills revived host SF240–246 and launches guest SF304. Return reverses this through another composer restart801, host SF fallback817 and original zygote/system_server reconstruction. Its broad kills/absence gate are not a retained resume. Commands are source facts; comments about earlier runs are not new runtime observations.

Sparing only system_server does not withdraw its original physical framework. The already-initialized Samsung startup explicitly constructs PhoneWindowManager1255, passes original Context/InputManager/policy/ATM to WMS.main1262, installs WMS's input callback1336→IMS.setWindowManagerCallbacks1340, starts IMS1343, calls DMS.windowManagerAndInputReady1356 and WMS.displayReady2247. These saved `SystemServer.startOtherServices` callsites identify the coupled original owners; they provide **no reversible stop/drain/rebind contract** for those live objects. They are initialization edges, not instructions to replay them.

Thus neither killing only host SystemUI nor freezing hostSS is a closed cut. The former does not account for WMS/IMS/DMS/AM/power or keyguard callbacks; the latter halts real StrongAuth alarms/handlers, users/policy and biometric work. Keeping host zygote instead also requires the already-identified real app-start/socket/control routing. Retention must first replace the coordinated stop/kill/keeper/watchdog/return assumptions and preserve the original source/state view; this plan does not reopen or solve the separate data-view/native-writer work.

The smallest physical **implementation boundary still missing** is an acknowledged withdrawal of host physical window/surface/input ingress while keeping the exact original policy producers operational, followed by one admitted guest physical owner. It must cover cached native display connections and real reader/dispatcher/composer ownership, not merely global service aliases, a stopped foreground process or absent PID. No such source-proven host API is present in the reused receipts. Do not invent a `headless` flag, disable all callbacks, null DMI to skip initialization, or implement a generic success acknowledgement. The installed composer/SF takeover must remain fenced until that owner exists.

## Narrow actual keyguard-policy cut

Samsung `TrustManagerService.refreshDeviceLockedForUser(II)` obtains its own `WindowManagerGlobal.getWindowManagerService` at53, uses genuine `LockPatternUtils.isSecure(user)`93 and TrustState124, branches on its actual current user136/138, reads genuine biometric-unlock state145, and queries **that WM's** `isKeyguardLocked()`150. The ordinary current-user decision220–235 combines those source values; background/visible-user/profile and the second-int exception branches remain real separate policy. A WM RemoteException takes the original conservative locked path165. Calling refresh alone rereads the host view.

Finite counterexample, inferred from that body: for a secure current user with neither genuine trust nor biometric exemption, guest keyguard can be physically locked while the old host WM result is false. The untouched method follows the false-WM branch to its unlocked device-state result. The opposite stale host view can leave Samsung policy locked after genuine guest authentication. These are unclosed source cases, not observed phone failures or proof of native key acceptance.

The candidate narrow seam is **only the actual WM observation at150 plus its real refresh-event ingress**, scoped to this original policy consumer. An admitted source must originate in the real current guest keyguard/WMS getter, carry its actual user/profile/display/source identity, and retire on source loss/replacement. The saved guest refresh itself calls `IWindowManager.isKeyguardLocked()`192, establishing a concrete guest consumer, but the getter's policy/occlusion semantics and its exact state-change publisher/receiver have not been traced here. A same-name method or showing Boolean is not that proof. Root should close those exact producer/getter/event edges before choosing transport; no honest authored owner interface or endpoint can yet be supplied.

Do not replace the global `window`/WindowManagerGlobal cache or call `setDeviceLockedForUser(user,bool)` from the frontend. Keep Samsung's full original refresh computation and its real user/trust/biometric state. Keep its setDeviceLocked body, including unchanged-state DualDAR processing71/80, trust agents, Keystore141, listeners144 and enabled-profile work. A scoped typed observation route must preserve the actual failure behavior and source subject; no default-user0, false-on-error, UI-dismissal-to-unlock or fabricated host lifecycle event.

There is also a concrete competing sink: acquired staged guest Trust remains body-identical to donor on these paths. Its `setDeviceLockedForUser` keeps its own map15 and listener27, but also invokes `notifyKeystoreOfDeviceLockState`24 **and49 for enabled profiles**; that helper attempts onDeviceLocked26/onDeviceUnlocked33 and does not make its return a native acceptance acknowledgement. A retained Samsung policy owner plus these unmodified guest physical-key notifications can issue contradictory policy attempts. The smallest candidate guest adaptation is those exact physical-notification edges with every reached profile path accounted for, preserving genuine guest UI/listener state and forwarding real keyguard events into Samsung's original policy. Do not delete the whole guest Trust service, manufacture successful native replies or suppress Samsung's own notifications. This is a coupled adaptation, not a ready two-NOP leaf: required additional callers/permissions/event ownership remain unclosed.

## Smallest honest construction sequence

1. **Retain before existing teardown.** Select the coherent original process/zygote/watchdog/socket/return profile already identified in retained-authority-control; keep real policy/user/native workers running. The capture diagnostic checks objects only and cannot satisfy this process lifetime. Keep guest physical start and competing security/policy publication fenced while doing this.
2. **Close the two real owner cuts before selecting display takeover.** Pin the actual live host WMS/IMS/DMS physical withdrawal/completion boundary; separately pin the real guest keyguard getter/event owner and its mapped physical user/display. If original policy cannot stay live after physical withdrawal without being replaced by fake state, reject this retained dual-framework cut. Do not broaden into another cold-service constructor exercise.
3. **Bind policy before publishing guest keyguard.** Implement a reviewed scoped observation/event route into the actual original Samsung Trust owner, retaining its whole policy body. At the same boundary, adapt the guest's two known native Keystore notification sites and close any further reached callers, while preserving real frontend events and genuine Samsung credential/StrongAuth/additional-factor finish gates. Unknown source or mismatched user/display leaves handoff unready; a view callback is never native auth.
4. **Transfer physical ownership once.** Only after real host withdrawal and actual guest readiness may the composer/SF/input control branch run. Preserve the real Samsung biometric/power/context consumers through source-compatible delivery of actual physical awake/display/session/pointer state. Existing BiometricContext uses real window/statusbar/session inputs, and Samsung DMI listener members are absent in the selected guest. UDFPS/TSP/illumination/overlay/error/cancel work remains real where features require it. The two cached DMS metadata reads71→44/86→59 are insufficient for this lifecycle; no all-UI no-op or spoofed sensor classification is permitted.
5. **Return through the reverse admitted boundary.** Close and actually drain guest physical/UI/keyguard ingress and relevant active work before restoring host physical ownership and callbacks. Keep the same Samsung policy owner, or retire it genuinely before reconstruction. Do not execute the current broad-kill/absence/restart return against a claimed retained server, start a second stock authority, or treat process death, a queue marker or a new SurfaceFlinger PID as native/input/policy drain.

The immediate engineering next action is therefore a **bounded paired keyguard getter/event-owner proof and a concrete host physical-withdrawal owner**, not a runtime API fabricated from hashes or booleans. If either cannot close without losing required original policy/native producers, this retained physical-display/input design is disqualified and root must select another full-goal architecture. Existing evidence establishes the exact present conflict and the necessary seam; it does not establish general impossibility, performance, real key/CE/auth behavior or a working switch.
