## Capture API and adoption order

Preserve existing eligibility restrictions, actual main-thread enforcement, current permit/profile checks, fixed bounded diagnostics and one attempt. Preserve private strong fields for the actual Registry and add one for Family. The exact success contour is:

1. `r = PreparedRetainedUserRegistryCapture.captureExisting()`; immediately assign `captureOwner = r` before another check, capture call or logger.
2. `r.checkStillBound()`; a versioned Registry-only progress code may be reported here. It never represents Family success. Any logger return/reentry is followed by the next capture's own genuine source checks.
3. `f = PreparedRetainedSecurityFamilyCapture.captureExisting(r)`; immediately assign `familyOwner = f` before another check/logger. The real method includes same-registry SMS/SMI comparison before its original marker monitor.
4. `f.checkStillBound()` and `r.checkStillBound()`; only then emit a versioned combined-bound code. Failure retains every already-acquired record and reports only a fixed refusal/stage code. Never null/drop owners, retry or fake a full result after a partial capture.

Registry/Family stay private; no new getter, authority issuer, current-user query, auth/enrollment operation or policy clearing. The Family marker monitor can block on genuine main-thread user work; this proposal adds no timeout surrogate, fallback lock or wall-clock guarantee.

## Two entry choices for root

**A: retain the existing post-original phase1000 hook.** Keep `chain.proceed()` outside the diagnostic catch and preserve its result/Throwable. The current acknowledged-hook/exact-target/main/permit/one-attempt gates remain. Replace only the capture block with the above sequence. This is the smallest hook-path source change, but late callback delivery can install after phase1000 and never capture that process. No replay, polling, current-phase backfill or automatic extra restart is included.

**B: one immediate task on the already-existing main Looper, without a hook.** If root establishes actual delivery of the new module into the intended already-running original system_server, let `onSystemServerStarting` admit exactly one scheduling attempt, obtain `Looper.getMainLooper()` and create an actual SDK `Handler(main)`. Retain the Handler before `post(this)`; Module implements Runnable. Do not prepare a Looper, spawn a thread, reflect a lifecycle target, call/replay a boot phase, poll or reschedule. `run()` independently checks the main thread, eligibility/profile/permit and consumes the capture-attempt latch before the sequence above. Capture's actual phase>=1000/late-marker/owner checks refuse an early or inconsistent graph. Refusal is terminal for this module attempt.

`post(true)` means enqueue acknowledgement, not capture or completion. The task may execute before post returns; a later QUEUED report must not overwrite/regress a terminal outcome or be required to precede it. Adopt the Handler before posting and keep scheduling uncertainty explicit on a throw; do not infer that no task ran from a failed caller-side return. Keep single scheduling/capture latches and separate progress codes rather than a generic success Boolean. Queue ownership lasts through dispatch only: sustained retention after run must use Vector's actual existing module-instance/loader owner. Instance fields or a static self-cycle alone do not prove process lifetime. If that owner is unproved, only immediate capture/check evidence is earned.

**Delivery remains a concrete gate.** Existing Vector evidence shows an early startup dispatch (`p.intercept`) and a late process-start dispatch (`u1.b(ZZ)` after critical-services reporting). It does not itself prove that newly enabling/installing a module delivers its callback into an already-running system_server. Root must select the actual delivery route/source or obtain the appropriate bounded observation. The posting alternative avoids waiting for a future phase only after callback delivery; it cannot supply injection. An early callback's one task may refuse, without a retry. The current `autoHotReload=false`/`onHotReloading=false` also prevents assuming a same-package update replaces already-loaded v1 classes. Require fresh v1-absent/module-state preflight or a separately selected package/lifecycle strategy; a different package alone still does not prove live delivery.
