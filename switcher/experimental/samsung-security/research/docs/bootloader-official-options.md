# Official bootloader options: bounded feasibility

Research checked 2026-11-06 UTC. **No Samsung-published unlock procedure or eligibility statement for this exact SM-S948U1 / SM8850 / BZIG build was located in the bounded primary-source search.** This is an evidence gap, not proof that every U1 device is permanently impossible to unlock. Bootloader-mode reachability and an accepted unlock interface have not been tested. No device operation follows from this report.

These are reported properties, not independent bootloader attestation. KG's numeric state is unassigned here; the differently suffixed display/bootloader identifiers do not establish a changed hardware identity.

Samsung's [model support page](https://www.samsung.com/latin_en/support/model/SM-S948UZVAPCT/) identifies SM-S948U1 and lists Android 16/17 manuals, but the inspected page supplies no bootloader-unlock route. Its regional support listing is not an eligibility certification for this phone. Samsung's [carrier-switching documentation](https://www.samsung.com/us/support/answer/ANS10002910/) concerns SIM/eSIM network service and carrier requirements. A carrier-unlocked phone or “U1” label does not thereby establish bootloader-unlock permission.

[AOSP's unlock specification](https://source.android.com/docs/core/architecture/bootloader/locking_unlocking) distinguishes the build capability property `ro.oem_unlock_supported` from the bootloader's current `get_unlock_ability` permission. Its reference flow requires OEM-unlock enablement, physical confirmation and a factory data reset. Thus observed supported=`1` warrants investigating eligibility, not claiming authorization or successful unlock. AOSP's generic fastboot flow does not prove that Samsung implements that transport or command on this build. Neither the current ability value nor an exposed OEM-unlocking control was established in this research.

[Samsung Knox's hardware-backed-security documentation](https://docs.samsungknox.com/admin/fundamentals/whitepaper/samsung-knox-mobile-security/system-security/hw-backed-security/) describes irreversible rollback fuses and a permanent Warranty Bit recording nonapproved states. If that bit is set, device-bound wrapped-key data can become inaccessible, and Knox-dependent functions can be blocked even after reset. Its [enterprise FAQ](https://docs.samsungknox.com/admin/knox-platform-for-enterprise/faq/) specifically identifies loss of existing Workspace data and services including Samsung Pay and Secure Folder after a trip. These sources do not establish the exact trigger timing for an unlock-only operation on BZIG; neither a Knox-safe unlock nor survival of existing credentials, enrollments or app keys is demonstrated. A later relock/reset is not documented as undoing the fuse. These consequences conflict with assuming the existing security state can simply be preserved through an unlock.

The bounded search included exact model/build terms, Samsung/Knox/AOSP sources and exact-model/SoC original-project discovery. No original-researcher project was verified to demonstrate an unlock for this exact U1/BZIG combination. Other vendors sharing SM8850, kernel temporary-root reports, forum assertions, commercial services and generic Samsung guides were not accepted as device-specific unlock evidence. No exploit, firmware, tool or paid service was downloaded or used.

The useful remaining feasibility questions are exact Samsung eligibility, the genuine exposed OEM-unlock permission state, and the actual supported bootloader interface. Root coordinates any further read-only evidence. This report grants no reboot, factory reset, unlock, flash, downgrade or security-state change, and leaves the existing project selections unchanged.
