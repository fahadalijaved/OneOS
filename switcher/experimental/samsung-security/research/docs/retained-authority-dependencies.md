# Retaining the initialized Samsung security authority

**Retaining the original initialized Samsung process is a concrete alternative to cold reconstruction, with a real source-backed advantage: keep the actual owners instead of rebuilding them. It is not currently an admitted OneOS topology.** The original process must remain operational with the correct state, endpoints and producers. Keeping a PID, pausing the process or preserving some cached Binders is insufficient. This report selects no architecture pivot and implements no retainer, service hook, publication or module activation.

No current device objects or initialized instances were inspected. “Retained” below means the proposed continuation of the original owners identified by captured Samsung source, not observed runtime retention. The [inventory](../inventory/retained-authority-dependencies.json) reuses ten frozen inventories and 17 bounded method bodies, checks 18 exact instruction edges and records cached/reconnection/callback sites. No new OEM body query was needed. Run `python -B tools/audit_retained_authority_dependencies.py` for the static recheck; raw evidence remains ignored. PCs in the table are **decimal DEX code units**.

## Cached owners do not survive arbitrary global changes

Two exact examples prevent treating cached native handles as a complete namespace solution. LSS.getGateKeeperService reads `mGateKeeperService` at1; when absent it waits on literal `android.service.gatekeeper.IGateKeeperService` at10, links death28 and stores the resulting interface47. Samsung SMS.connectVold$1 looks up literal `vold` at3, links death22 and assigns `mVold`33 before original listener/reconnect work. A currently retained original handle can avoid a new lookup; it does not close later cache-miss/death/reconnect routing to the correct generation. Do not probe an unidentified native service using Samsung transaction numbers.

FingerprintProvider.getHalInstance similarly retains the actual `mDaemon`, but acquisition/reacquisition links native death, reads genuine alive users and schedules cleanup/authenticator-ID loading. A new daemon or wrong metadata view cannot be treated as the former session. Existing OneOS native PID checks cover only selected names; they do not establish FP/Weaver/KeyMint sessions or completion. The [biometric gate](authority-bootstrap-biometrics.md) records required current-user observers, BiometricContext's real window/statusbar/session/dock inputs, feature-dependent display/TSP/illumination/power work and the deferred real Samsung BiometricsUIService binding. Disabling all host UI/display/power work is not a source-proven security-only cut.

State also includes future accesses, not just open descriptors. OneOS prepares staged app/user/user_de/profile/media/resource-cache overmounts before launching its new guest mount namespace. A retained multithreaded host server is not moved by that later guest `unshare`; every real worker needs the correct original source/state view. Preserve legitimate live CE/mount changes rather than freeze an arbitrary snapshot. Original cached properties/features can coexist with later global property reads, producing an unadmitted hybrid when OneOS injects guest properties. The real first-API/FBE/HSUM policy must remain coherent; never force a false/default or drop a HAT to hide a mismatch.

Shade's [control card](retained-authority-control.md) independently pins the actual stop/kill/keeper, watchdog, host-view mounts, zygote sockets, ambiguous PID selectors and return gates. Its captured init declarations prove neither inevitable system_server death nor safe survival after stopping zygote. Removing one kill or renaming the process addresses none of these dependencies.

## Which producers must remain live or be transferred exactly

The proposed retained authority must continue serving genuine credential and policy work. StrongAuth owns its main-Looper Handler, AlarmManager deadlines and alarm callbacks; suspending the process prevents policy updates. LSS.unlockUser calls cached original AM.unlockUser2 at42, waits15 seconds without using the wait Boolean, then posts biometric work. Keeping host AM while guest AM is active does not automatically synchronize user unlock progress or intended guest CE state. Guest-local UMI/LockSettingsInternal callers and original host UserController must describe the same authoritative users and serials, with real ordered lifecycle events—not two independent state machines claiming success.

DPM/Supervision/Role/settings and SecureLockDevice controllers must retain genuine policy changes and callbacks. Fingerprint needs active schedulers, lockout/StrongAuth, native sessions, user observers, display/context/input/illumination and deferred UI connection ownership. Credential removal can invoke real FP/face removeAll; a timed wait or empty Java queue does not certify template deletion. Keep the genuine producers until a source-preserving replacement and actual child/native completion is demonstrated. Optional host foreground/presentation work may eventually be gated, but this report finds no safe blanket host-UI no-op boundary.

## Minimum concrete topology to investigate

This is an **inference/proposal**, not an available runtime:

1. Keep the original Samsung system_server, original initialized graph and required live policy/native/callback workers. Suppress competing guest credential/biometric writers before their constructors. Do not construct another LSS/UMS/DPMS/FP family merely as a bridge.
2. Preserve the whole-thread original code/resource/state/native view before OneOS mount/property/zygote control changes. Investigate isolating guest-only preparation deliberately; do not assume an initialized multithreaded process can be relocated safely after overmounts. Keep one real CE/enrollment/credential writer and controlled legitimate mount propagation.
3. Host the guest-protocol Binder frontend **inside that same original process**, retaining the actual original Samsung Stub/backend. A direct guest Binder call can then reach the original checks without an extra remote dispatch hop or native caller impersonation. The current prepared routes are conditional components, not an installed frontend or real source admission.
4. Keep Samsung internal canonical endpoint routes coherent. Give guest framework services explicit separate publication/lookup/reconnect routes and real guest-local proxies where required. This is a logical namespace requirement, not proof that an independent Binder driver context can exchange existing handles/callbacks. Same-driver aliases likewise need actual complete routing; process-local LocalServices cannot be remotely shared by name.
5. Bind genuine guest package/UID/user/profile/permission/AppOps/attribution identity to the original policy owners. LSS.checkWritePermission directly calls its original Context.enforceCallingOrSelfPermission at8. Preserving the incoming native UID does **not** prove host PM/AM recognizes the guest package, permissions or intended app key namespace. UID1000 alone is not authority admission. No permission relaxation, fake package identity or caller-supplied UID is proposed.
6. Establish exclusive physical display/input/power and biometric UI ownership while preserving required original callbacks. On return, drain the guest operations and resume the same authority **or** truly retire it before stock reconstruction. Never start a second stock LSS beside the retained writer. Reboot and reciprocal PIN/FP/per-use crypto/CE acceptance remain the full GOAL.

## Comparison and decisive gate

Retention trades **cold graph reconstruction** for **live dual-framework coexistence/control**. It can avoid the current cold Context/display, private-class/JNI, user/policy constructor and early-cleanup obligations, while continuing existing native/deferred work with its real owner. It retains a broad running framework and may keep services/apps needed by actual callbacks; memory, scheduling, thermal and latency costs are unmeasured. Cold reconstruction seeks a smaller owner but still has the frozen constructor/loader/source/native/state/handoff gaps. Counts of prepared adapters or PC tests do not rank either architecture as working or fastest.

The next useful decision gate is one concrete retained-instance ownership sheet across **parent/zygote/watchdog; whole-thread state/mount/property view; host/guest endpoint+local lifecycle routes; package/UID/user/policy; physical/native biometric owner; return/drain**. Disqualify retention if a required original owner cannot remain operational or be coherently supplied, native/physical writers conflict, live guest identity cannot be admitted, or safe return requires a second writer/default policy. Conversely, a demonstrated sheet would justify investigating an actual retained-source hook before more cold reconstruction. No such owner, hook, device test or architecture pivot is supplied here.

Peer exchange with Shade incorporated the concrete switch/return collisions and the critique that freezing hostSS or no-oping host UI would lose real security producers. The control card makes no stronger survival claim; this dependency card makes no stronger namespace/native/runtime claim. Both remain scoped source proposals with no phone/OEM execution or old artifact edits.
